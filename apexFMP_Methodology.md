# apexFMP Methodology

Author: Joseph E. Arzate Jr.

## A FileMaker-first UI architecture using HTML, CSS, JavaScript, and FQL

### Overview

apexFMP is a development methodology that fuses FileMaker Pro with modern web front-end techniques. It treats the UI as an HTML-based presentation layer, while keeping the data, logic, and relationships in FileMaker. In this model, FileMaker remains the system of record and business rules engine, but the user interface is built in HTML, styled with CSS, and enhanced with JavaScript.

This approach emerged from a simple observation: traditional FileMaker layout design is powerful for rapid form building, but it becomes cumbersome when you want to create highly customized, scalable, reusable, and AI-friendly interfaces. With FileMaker's web viewer, JavaScript bridge, and FQL capabilities, the UI no longer has to be constrained to FileMaker's layout mode and layout object model.

This methodology was shaped by corporate experience, where FileMaker was often treated as the outlier in an organization that otherwise operated on traditional software development patterns. It was frequently viewed as a specialized tool that had to be approached differently from the rest of the technology stack, even when it was doing the same core work: managing data, workflows, logic, and user interaction. That experience created a clear motivation: FileMaker should not have to remain isolated from modern engineering practices simply because it is FileMaker.

The result is a method where HTML pages become form templates, FileMaker becomes the data and process engine, and a data-driven merge system turns raw templates into fully rendered web interfaces.

The strongest version of this methodology is a disciplined architectural model: FileMaker remains the system of record, the relationship engine, and the business rules platform, while the interface becomes a web-native, code-driven layer that is easier to version, review, and scale with modern software practices. This aligns FileMaker development much more closely with the broader traditional software stack, for the most part, without abandoning the strengths that make FileMaker such a powerful platform in the first place.

---

## Why this methodology exists

Traditional FileMaker development is often highly visual, but also highly constrained.

Typical FileMaker techniques rely on:

- WYSIWYG layout mode
- Dragging fields, boxes, and buttons onto layouts
- Managing visual behavior inside a closed UI system
- Repeating patterns manually across many layouts
- Difficulty scaling UI work into more modern front-end patterns

This is not a flaw in FileMaker. It is simply a limitation of the tool when it is used as a full UI authoring environment. FileMaker is excellent at data modeling and workflow, but the interface layer is less flexible than modern browser-based UI systems.

apexFMP acknowledges that reality and intentionally separates the layers:

- FileMaker handles data, relationships, rules, and workflow
- HTML/CSS/JavaScript handle interface design, responsiveness, and interactivity
- FQL and merge substitution handle data delivery into the template
- The web viewer becomes the rendering container

The goal is not to abandon FileMaker. The goal is to use FileMaker where it is strongest and use the browser where it is stronger.

---

## Core Principle

The core principle of apexFMP is simple:

> Build the UI as HTML templates, store them in a central system, inject FileMaker data by merge variables, and render the final page in a FileMaker web viewer.

This means the HTML file is no longer just a static page. It becomes a reusable form template.

The methodology is strongest when the team clearly defines the boundary between system authority and presentation logic. FileMaker should remain the authority for data integrity, security, workflows, and relationship behavior. The browser should be treated as the environment for UX, interaction, and presentation-layer calculations.

A template may look like this:

```html
<div id="fm-query-results" style="display:none;">{{QueryResults}}</div>
```

That placeholder is later replaced with real JSON or text generated by FileMaker. Once merged, the HTML becomes a concrete rendered interface for the user.

This is the heart of the method: templates are authored in a modern web environment and then hydrated with live FileMaker data.

### Operating principles and guardrails

To make the method durable in real teams, a few guardrails matter:

- FileMaker remains the source of truth for records, relationships, permissions, and business rules.
- HTML/CSS/JavaScript are treated as the presentation and interaction layer.
- Every merge variable must be documented and tied to a clear data contract.
- UI payloads should be structured and predictable so they can be reviewed like any web API contract.
- Calculations used only for display, summaries, and interaction should be implemented where they are most maintainable, often in JavaScript.
- Critical financial, security, and transactional logic should remain in FileMaker.
- UI assets should be versioned in Git and reviewed through pull requests like any software artifact.

These guardrails are what separate a practical architecture from an interesting experiment.

## The architecture

apexFMP is built on a few simple but powerful design principles:

### 1. UI is authored as HTML

All form layouts are created in a code editor such as VS Code, not in FileMaker layout mode. This allows for:

- faster iteration
- cleaner structure
- component reuse
- AI-assisted code generation
- stronger version control and diffing
- easier styling controls with CSS

The HTML file becomes a form definition. Each page is effectively a UI template.

### 2. Merge variables hold dynamic content

Wherever UI needs runtime data, the developer inserts hidden placeholders such as:

- {{QueryResults}}
- {{ListEditors}}
- {{RecordData}}
- {{ExistingCustomer}}
- {{ListSchools}}

These placeholders are not random tokens. They are explicit data contracts between the UI and FileMaker. The JavaScript in the page reads those values, parses them, and then populates the interface.

### 3. FileMaker provides the data

FileMaker executes FQL or other supported functions to produce the data that will be inserted into the template. This data is usually converted to JSON so the JavaScript can parse it cleanly.

This is one of the most important architectural advantages of the method: the merge code is not limited to a relationship-driven FileMaker pattern. Instead, each merge variable can call an FQL query that behaves much more like a standard SQL SELECT statement. A developer can write a query with `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, and `ORDER BY` logic, and retrieve exactly the data needed for the current form without building a custom relationship graph just to support that page.

In traditional FileMaker development, a developer often creates relationships to support a layout, portal, value list, or lookup. Those relationships may be necessary for the system, but they can also create a lot of hidden coupling between tables, layouts, and UI behavior. In apexFMP, a form can simply declare what data it needs through a merge code, and the FQL query can gather that data directly from the underlying tables.

This is a major shift because it makes the UI more intentional and more modular. Instead of a form depending on a preexisting relationship path, it declares a data contract in the formVariable table. The query resolves the data from the schema directly. If a form needs records from a customer table and a related school table, it can join them in one query. If it needs summary totals by sales rep, it can aggregate them in the query and deliver the pre-shaped result set to the UI.

### The evolution toward HTML-first FileMaker development

A significant strategic point in this methodology is that it aligns with the direction FileMaker appears to be moving toward. FileMaker's increasing adoption of web-centric capabilities, HTML-based rendering patterns, and developer-friendly export/import constructs such as XML-based file serialization are not isolated features. They are a signal that the platform is increasingly moving toward a more conventional, code-oriented software model.

This matters because the platform is gradually becoming more compatible with the way modern software teams think about application interfaces: as structured, versionable, inspectable, and transportable artifacts rather than as visually embedded layout objects locked inside a proprietary authoring environment.

The ability to save a FileMaker file as XML and treat the file as an artifact that can be inspected, patched, manipulated, or generated through tooling is a strong indicator that FileMaker is heading toward a more open, text-readable, and developer-aligned model. In other words, the platform is increasingly supporting a workflow where software can be treated more like source code and less like a single opaque desktop document.

apexFMP fits naturally into that direction. It embraces the idea that the UI can be authored and managed in a modern, structured, source-controlled format. A form is not just a layout object inside FileMaker; it is a template, a data contract, and a code artifact that can be reviewed, versioned, and evolved using engineering practices that are already common across the web stack.

This is where the methodology becomes more than a front-end pattern. It becomes a forward-compatible strategy for FileMaker in a world where UI engineering, automation, AI tooling, and source control are increasingly standard expectations.

In practical terms, this means the developer can write queries that look familiar to any SQL-oriented developer:

```sql
SELECT s.id, s.name, COUNT(o.id) AS totalOrders
FROM staff s
LEFT JOIN sales o ON o.salesRepId = s.id
WHERE s.active = 1
GROUP BY s.id, s.name
ORDER BY totalOrders DESC
```

That style of logic is not just more portable. It reduces the amount of relationship management required purely for presentation needs. FileMaker still provides the authoritative data model, but the UI no longer has to be built around a rigid network of layout-driven relationships for every data fetch.

### 4. A web viewer renders the final output

The FileMaker web viewer loads the merged HTML page, which now contains live data and interactive JavaScript. The user sees a modern interface, but the business logic and persistence remain in FileMaker.

## The standards model

The methodology depends on a small, consistent pattern:

### sysUI table

This table stores the raw HTML template or reference to the template.

It acts like a centralized UI repository.

Example concept:

- sysUI::id
- sysUI::formName
- sysUI::htmlSource
- sysUI::version
- sysUI::isActive
- sysUI::description

This is the central table for all forms.

Instead of a layout being spread across FileMaker layout objects, the UI is stored as HTML in a single data source.

### formVariable table

This table stores the merge codes and associated data-generation logic for each form.

Each form can have many merge variables, and each variable can describe what data to load and how to format it.

Example concept:

- formVariable::id
- formVariable::sysUI_id
- formVariable::mergeCode
- formVariable::fql
- formVariable::description
- formVariable::sortOrder

Example record:

```text
mergecode: {{QueryResults}}
fql: SELECT name FROM customers
```

This table creates a clean data contract between the UI and the data source.

## The lifecycle of a form

The flow is designed to be predictable and repeatable.

### Step 1: Build the template

The developer creates the HTML file in VS Code and writes the structure, CSS, and JavaScript. The template contains placeholders like {{QueryResults}} or {{ListCustomers}}.

This stage is ideal for AI-assisted development because the UI logic can be described in plain language and generated rapidly.

### Step 2: Store the form in sysUI

The template is stored in FileMaker so it can be retrieved by script later. In a basic implementation, the HTML source is saved directly to a table. In a more advanced implementation, FileMaker can fetch the HTML from an API or repository.

### Step 3: Define merge variables in formVariable

Each merge code is associated with the form and mapped to an FQL query.

Example mapping:

```text
{{QueryResults}} -> SELECT * FROM customers
{{ListSchools}} -> SELECT id, name FROM schools
{{ListEditors}} -> SELECT id, name FROM staff
{{ExistingCustomer}} -> SELECT customerName FROM orders WHERE id = ?
```

This gives each form a precise and structured data contract.

### Step 4: Load the form in FileMaker

A layout or script navigates the user to a form page. A FileMaker script identifies the template record and retrieves its associated variables.

### Step 5: Resolve each merge code

The script loops through each formVariable record related to the UI record. It executes the FQL, serializes the result as JSON, and substitutes the placeholder text inside the form template.

For example:

```text
{{QueryResults}} becomes [{"id":1,"name":"Acme Books"}, ...]
```

### Step 6: Render the final HTML in the web viewer

Once all merge codes are replaced, the web viewer displays the final HTML page. The page's JavaScript reads the JSON data, populates fields, builds tables, populates dropdowns, and enables interaction.

### Step 7: User action triggers FileMaker script bridge

When the user clicks a button, submits a form, or changes a row, JavaScript sends a structured payload back to FileMaker through the FileMaker script bridge.

This payload may include:

- formName
- module
- action
- formParam

This is the point where FileMaker receives user interaction and routes the request to the correct process.

## FileMaker technical patterns that make apexFMP practical

apexFMP is not simply a design philosophy. It is built on a specific set of FileMaker capabilities that make the architecture practical and powerful.

### FQL

FQL is the data-shaping layer that allows the application to retrieve exactly the data required for a form. It behaves much more like SQL than traditional FileMaker relationship-driven record access. A developer can use `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`, and other query patterns to return a compact, purpose-fit result set for a page or widget.

This is especially valuable in a UI architecture where each template only needs a small, explicit slice of data. Instead of forcing a layout to follow a relationship graph, the page can request the exact data it needs and receive it in a clean JSON-friendly structure.

### Set Field By Name

The Set Field By Name function is a critical pattern when forms are generated dynamically. In an apexFMP-driven application, the payload often contains field names and values, and the FileMaker side must map those names to the correct table fields without hardcoding every field in a custom script.

This allows a developer to process a generic payload such as:

- fieldName = "customerName"
- value = "Acme Books"

and then use Set Field By Name to write that value into the correct field in the proper table. This turns the system into a more data-driven form engine rather than a set of hand-built per-form scripts.

### Evaluate

Evaluate is a powerful FileMaker capability when logic must be generated dynamically. In apexFMP, a form may need to execute a formula or script expression built from metadata or a passed-in calculation string. Instead of requiring a unique script for every possible condition, a developer can assemble the formula at runtime and evaluate it.

This is especially useful for:

- dynamic validation rules
- computed formulas stored in metadata
- conditional output built from user or form context
- building generic script logic around data contracts

The result is a more flexible and extensible engine without creating excessive scripting sprawl.

### JSON

JSON is the canonical bridge between FileMaker and the web layer. FileMaker produces JSON from query results, merge variables, or payload structures, and the browser parses it using JavaScript.

This is essential because the HTML page does not interact with FileMaker objects directly. Instead, FileMaker provides a structured payload or dataset, and JavaScript reads it and renders the interface. JSON is the common language that makes this architecture efficient and maintainable.

### Perform JavaScript in Web Viewer

This capability is the glue that binds the UI to FileMaker interaction. A web viewer can render HTML and CSS, and then the FileMaker layer can instruct the browser to run JavaScript in that viewer. This allows the app to refresh controls, perform UI validation, compute totals, apply filters, and trigger event-driven responses without leaving the web-viewer experience.

This is what turns the web viewer from a passive display surface into an active application layer.

### Web Viewer

The web viewer is the rendering container that makes the whole method possible. It allows FileMaker to display modern HTML, CSS, and JavaScript while preserving the system as the application shell. This gives the developer the benefit of a browser-based UI while keeping FileMaker as the data and workflow core.

Together, these FileMaker-native capabilities create a hybrid architecture that is both practical and scalable:

- FQL retrieves the right data
- JSON moves that data into the browser
- JavaScript renders and transforms the interface
- user actions return structured payloads
- FileMaker receives those actions and applies business logic, writes data, or routes the request through the proper process

This is a mature architecture because it uses FileMaker's strengths in the right places without forcing the interface to live inside FileMaker's layout model.

## Why this is powerful

### 1. UI and data are separated cleanly

This is the biggest conceptual shift.

In traditional FileMaker, the interface and data model are tightly coupled in layouts and object references. In apexFMP, the UI is a template and the data is injected at runtime. This makes the front end far more flexible and decoupled from the data layer.

### 2. The front end is easier to build with modern tools

HTML, CSS, and JavaScript are far more expressive than FileMaker layout mode for interface design. AI tools and web-native design systems work much better in this environment than they do inside FileMaker's visual layout engine.

This means:

- faster UI development
- reusable components
- better visual design consistency
- more maintainable code

### 3. Forms become central assets

Instead of many layouts in FileMaker, there is a single data-driven collection of form templates.

That creates a central registry of interfaces and makes it easier to:

- track versions
- reuse forms
- deliver standardized modules
- manage UI changes in one place

### 4. Merge logic makes data delivery explicit

The formVariable model is important because it turns each piece of data into a named contract. You know exactly which merge code is mapped to which data source and which query produces it.

That creates a strong pattern of maintainability and traceability.

### 5. The relationship graph remains data-centric

In FileMaker, the relationship graph has traditionally been overloaded with both data structure and UI logic. In apexFMP, the relationship graph is used primarily for data modeling and business relationships.

The UI no longer depends on layout objects or UI-specific FileMaker constructs. This makes the schema cleaner and easier to reason about.

### 6. Scripts become lighter and more finite

Instead of a large number of interface-specific scripts scattered across the app, there are small, reusable, finite scripts that:

- retrieve the form template
- resolve merge variables
- replace placeholders with JSON data
- send HTML to the web viewer
- route action payloads back to FileMaker

This greatly reduces complexity.

### 7. Calculations and summaries can move to the browser

A major strategic benefit of apexFMP is that many calculations previously embedded in FileMaker as calculation fields, summary fields, or custom aggregate logic can be executed in the browser using JavaScript on the final JSON payload.

In traditional FileMaker development, teams often create: 

- calculation fields for totals and subtotals
- summary fields for grouped reporting
- unstored calculation logic for display-only values
- repeated formula patterns across layouts and portals
- niche business logic tightly embedded in a FileMaker-specific environment

These are powerful, but they also create a dependency on FileMaker-specific calculation patterns, especially when the same logic is needed for UI presentation, dashboard summaries, or row-level calculations that are more naturally handled by a modern web runtime.

With apexFMP, the application can fetch raw data from FileMaker, transform it into JSON, and then run JavaScript functions to calculate values such as:

- subtotal by row
- tax and shipping totals
- grand totals
- running totals
- percentage of total
- average price or margin
- grouped summary totals by customer, book, or sales rep
- dashboard KPIs and summary cards

This is not a rejection of FileMaker calculations. It is a repositioning of where that logic should live. FileMaker remains the source of truth for authoritative data and business rules, while the browser becomes a highly capable rendering and calculation environment for display-focused logic, user interaction, and summary output.

The browser makes this easy because JavaScript is well-suited for data transformation. Logic such as `reduce()`, `map()`, `filter()`, and array grouping can compute totals and summaries quickly and clearly. A developer can write code that is directly understandable, reusable, and easier to test than a spread of FileMaker-specific calc fields hidden inside layouts or reports.

This is especially useful for summary views, analytic cards, and dynamic table calculations that need to respond instantly to user selections without reloading the entire application or requiring a special FileMaker-only calculation model.

Example concept:

```javascript
const rows = JSON.parse(document.getElementById('salesData').textContent);

const totals = rows.reduce((acc, row) => {
  acc.total += Number(row.amount || 0);
  acc.tax += Number(row.tax || 0);
  return acc;
}, { total: 0, tax: 0 });
```

This kind of logic is simple, maintainable, and aligned with web development standards. It also reduces the need to build highly niche FileMaker-only summary patterns for display logic that is conceptually standard application math.

The result is a healthier architecture:

- FileMaker owns data integrity and core transactional rules
- JavaScript handles presentation-layer calculations and user experience behavior
- summary values are easier to inspect, debug, and maintain
- teams are not forced into FileMaker-specific calculation design for every UI summary
- the application can leverage standard web development patterns for calculation logic

This creates a cleaner division of labor. FileMaker remains the system of record and business rule engine, while the browser becomes the place for calculation-heavy presentation logic that is easier to build, review, and evolve using standard coding tools.

## Advanced considerations

### Advanced version

The most advanced form of this architecture is not to store HTML directly in FileMaker at all, but to fetch it from an external source such as:

- a Git-managed repository
- an API response
- a web asset server
- a CMS or content store
- a version-controlled UI folder

In that version, FileMaker acts like the application shell, and the UI source is retrieved dynamically. This creates a more enterprise-friendly architecture and allows the front end to be version-controlled and updated independently from the database engine.

### Security and control

Because UI is code and not layout objects, there is a stronger opportunity to define security and access rules around:

- which forms are available
- which merge data can be loaded
- which users can access which templates
- which actions are allowed in the script bridge

### Data shaping

Because the UI is fed JSON, the data can be shaped precisely for the user experience. This means the front end can consume clean, minimal, purpose-driven objects instead of forcing a layout to directly mirror the data model.

### Multi-device layouts

This method also scales well to different form factors.

The same form can be served in variants based on:

- screen size
- device type
- layout profile
- user role
- app mode

This is a clean fit for responsive design and device-specific UX rules.

## Git, pull requests, and alignment with the web stack

The most important strategic advantage of apexFMP is that it does not keep FileMaker development trapped inside a desktop-only, layout-centric workflow. Once the UI is authored as HTML, CSS, and JavaScript files, the project begins to resemble a modern web application architecture.

That means the development process can shift from a closed FileMaker-only model to a familiar software delivery pipeline:

- UI files live in a repository
- changes are committed with clear version history
- branches are created for features and fixes
- pull requests are used for peer review and signoff
- merge conflicts can be resolved in a standard engineering workflow
- release tags and deployment branches can be managed with conventional tooling

This is a major difference from traditional FileMaker development, where many interface changes are visually edited inside the application and are harder to review, diff, or audit in a structured way.

### Why this matters

Traditional web development already assumes a source-controlled, reviewable, and repeatable workflow. A developer creates a branch, modifies code, submits a pull request, and the team reviews the exact diff before merging. That same discipline becomes possible with apexFMP because the interface is now authored as code instead of as layout objects.

This creates a bridge between FileMaker development and standard engineering practices:

- HTML templates are versioned like front-end components
- CSS is managed like design-system styling
- JavaScript becomes application logic rather than isolated UI scripting
- merge variables become explicit data contracts rather than hidden layout behavior
- a feature branch can be reviewed without visual ambiguity

### The Git-based workflow becomes practical

A typical apexFMP workflow might look like this:

1. A developer creates a feature branch such as `customer-portal-redesign`.
2. The HTML template, CSS styling, and JavaScript behaviors are updated in a code editor.
3. Merge tokens and FQL contracts are adjusted in the FileMaker-side data layer.
4. The developer commits the changes with clear, readable messages.
5. A pull request is created for review.
6. Reviewers inspect the actual code diff, not just the resulting UI in a modal designer.
7. The PR is merged after validation.
8. The final form is deployed or refreshed in the web viewer environment.

This is a standard engineering lifecycle, and it is one of the biggest organizational advantages of apexFMP.

### It creates a true front-end/back-end split

In a traditional web stack, there is a clear split between:

- front-end presentation code
- back-end business logic
- data persistence and API contracts

apexFMP mirrors that model in a FileMaker ecosystem:

- FileMaker remains the backend and transactional engine
- HTML/CSS/JS become the front-end presentation layer
- merge variables and JSON payloads become the contract
- the web viewer acts like a rendered UI runtime, similar to a browser window or a front-end shell

This separation makes the application easier to reason about, easier to scale, and easier to integrate with modern tooling.

### Code review and governance improve

Because the interface is stored in text files, the team can now apply standard engineering governance:

- review changes before deployment
- enforce naming conventions and coding standards
- track regressions
- compare behavior across versions
- manage releases in a more predictable way

This is a major improvement over a layout-based FileMaker workflow, where the visual UI can be difficult to audit and often becomes tribal knowledge owned by a single developer.

### Pull requests enable safer evolution

With Git-based branching, a team can safely evolve the interface without disrupting a live FileMaker application. A feature can be built in isolation, tested in a controlled branch, and merged only after validation. This allows for:

- safer release cycles
- better collaboration
- reduced risk of ad hoc UI changes
- smoother handoff between developers and stakeholders

In other words, the UI begins to behave like a software product instead of a collection of manually edited FileMaker objects.

### This is not replacing FileMaker; it is making FileMaker more enterprise-ready

This is important to clarify. apexFMP does not attempt to turn FileMaker into a JavaScript framework or abandon its strengths. Instead, it gives FileMaker a more disciplined software architecture.

FileMaker still owns the things it is best at:

- relationships
- business rules
- auditability
- workflow automation
- transactional logic
- structured data storage

But the front end is now treated as a code artifact with the same engineering practices as a modern web project. That makes FileMaker more aligned with enterprise development teams, DevOps practices, and team-based workflows.

### In practical terms

The result is that a FileMaker app built with apexFMP can participate in a much more modern software lifecycle:

- Git repositories for UI assets and front-end code
- feature branches and pull requests
- code review and release management
- testable front-end behavior and payload contracts
- easier onboarding for developers coming from a web stack
- more standard tooling and CI/CD patterns

This is one of the core strategic reasons apexFMP is valuable: it does not merely improve how a screen looks. It changes how the application is built, reviewed, and maintained.

### Talent strategy and hiring model

This methodology also creates a more flexible hiring model for a company. When the UI is authored as HTML, CSS, and JavaScript, a team is no longer limited to hiring only developers who are deeply specialized in FileMaker layout work for every interface task. Designers, front-end developers, and engineers from standard web backgrounds can contribute to the presentation layer, component patterns, and interaction model using tools and workflows they already know.

That said, this does not reduce the need for FileMaker developers. It does the opposite: it makes their role more strategic. FileMaker professionals remain essential for the database structure, relationship graph, business rules, data integrity, security model, process automation, and complex workflow logic. They are the architects of the system's core operating model, while web developers can contribute more effectively to the interface layer and modern UI engineering.

The real effect is a broader, healthier talent ecosystem. A company can hire from both pools without forcing every contributor into a narrow FileMaker-only skill set. FileMaker developers continue to own the system logic, while web-focused developers contribute to presentation, interaction, and code-based UI delivery. This creates a team model that is stronger and more scalable, rather than replacing one specialization with another.

### Smaller application footprint and lighter file architecture

Another practical advantage of this approach is that the resulting FileMaker file can remain relatively compact compared to a traditional FileMaker application that stores a large amount of layout metadata, object definitions, styling rules, and embedded UI artifacts directly inside the file.

In a conventional FileMaker build, the database file often grows as the number of layouts, objects, custom themes, portal definitions, script attachments, and layout-specific styling increase. Those objects are embedded into the file itself, and the footprint can become substantial even when the underlying business logic is not particularly large.

In an apexFMP model, the app still stores the core data model, workflows, and business logic in FileMaker, but the presentation layer is moved toward externalized templates, cleaner UI assets, and more structured code. The file does not need to carry the same degree of visual complexity, because the interface is not being authored as dozens of tightly coupled layout objects embedded in the database structure.

This has a direct operational benefit:

- the database file can remain smaller and more efficient
- layout-related bloat is reduced
- the app is easier to manage structurally
- the front end becomes easier to version, review, and edit outside the FileMaker layout model
- the system can be more maintainable over time as the project grows

In other words, the application can keep the FileMaker strengths that matter most — data integrity, relationship logic, access control, workflow automation, and secure record management — while the UI layer is shifted into a more lightweight and standard code-based model.

This is a meaningful architectural benefit. The file remains more focused on business data and logic, while the interface becomes a more maintainable code artifact rather than a large embedded UI object graph.

## Final summary

apexFMP is a methodology for building FileMaker applications using a web-first interface model. It treats each HTML page as a form template, stores that template in a central repository, defines each dynamic placeholder via merge variables, and resolves them with FQL and JSON before rendering them in a FileMaker web viewer.

It is better than traditional FileMaker development because it separates concerns, uses modern UI tooling, reduces UI bottlenecks, centralizes form management, and makes the application architecture more scalable, maintainable, and compatible with modern web development patterns.

This approach does not reject FileMaker. It elevates it.

FileMaker remains the system of record and business logic engine, while the interface becomes a modern, web-native presentation layer that is more flexible, reusable, and powerful than conventional layout-based FileMaker development.

The most mature expression of apexFMP is where FileMaker remains foundational, but the organization gains the benefits of modern UI engineering: source-controlled front ends, better team collaboration, cleaner component patterns, broader talent access, and a more maintainable application structure without sacrificing the data quality and process integrity that FileMaker provides.

---

## Short definition

apexFMP can be described as:

> A FileMaker-driven HTML front-end architecture where templates are authored as HTML, dynamic content is injected via merge codes, FileMaker supplies the data through FQL, and the final experience is rendered in a web viewer.

That is the essence of the methodology.
